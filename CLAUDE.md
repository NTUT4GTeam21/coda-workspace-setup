# CLAUDE.md

Guidance for Claude Code when working in this repository. Read this before making changes.

## Project

A web toolkit that helps volunteers plan and run reading sessions with children of Deaf adults (CODAs), for SADeaf. Built by a team of six students (NTU Honours College Tech for Good, Team 21).

- **Users:** volunteers (primary) and SADeaf staff (secondary).
- **Not users:** children and parents never log in or see the app directly.
- Main loop: pick a book in the **Library** → run a **Session** → save notes to the **Child record** for the next volunteer.

## Stack

Generated by Lovable. Check `package.json` before assuming libraries. Expected: React, TypeScript, Vite, Tailwind CSS, shadcn/ui, with a Lovable Cloud / Supabase backend.

- Reuse existing shadcn/ui components and Tailwind tokens; do not add a new UI library.
- Do not add dependencies without saying why in the PR.

## Collaboration rules

- Six people work on this repo, plus Lovable, which commits directly to `main`.
- **Never commit directly to `main`.** Work on a branch named `feature/<name>` or `fix/<name>` and open a pull request.
- Keep changes small and scoped to one module. Do not reformat or refactor files outside the task.
- Before starting, pull/merge the latest `main` to avoid conflicts with Lovable's commits.
- Write clear commit messages in the imperative: `Add tricky-word quick-add to session page`.

## Data and privacy (non-negotiable)

- **Never commit real children's data.** Use obviously fake data such as `Child A`, `Child B`.
- Store the minimum: first name or code, level, words, short session notes. No surnames, photos, family details, addresses, or emotional disclosures.
- All child data must sit behind login. Enable row-level security on any table holding child data.
- **Never commit secrets.** API keys go in environment variables or the Lovable/Supabase secrets settings, not in code.

## Content principles

- Teaching stays human: the app prepares and records; volunteers teach.
- Prefer pre-written, reviewed content in editable tables over live AI generation (latency, cost, unchecked output).
- Any content a child might see must be reviewable by a person before use.
- Do not store copyrighted book files. Store titles, levels, links and our own notes only.
- Use Singapore Sign Language (SgSL) references, not ASL or BSL.
- Use plain, warm language suitable for volunteers; keep each guide card to one screen.

## Accessibility

- The audience includes Deaf and hard-of-hearing staff: never rely on audio alone, and caption any video.
- Use semantic HTML, labelled form fields, keyboard navigation and sufficient colour contrast.
- Layouts must work on a phone, since volunteers may use one during sessions.

## Keeping the team informed (required for every change)

Two tracker files live in the repo root. Update them in the same commit or PR as your code change.

1. **`CHANGELOG.md`** – add one line at the top of the "Unreleased" section:
   `- YYYY-MM-DD · <module> · <what changed, in plain English> (<author or "Lovable">)`
   One line per meaningful change. Skip typo-only fixes.
2. **`PROGRESS.md`** – update it only when:
   - a feature's status changes (Not started → In progress → Done), or
   - files or folders are added, moved or removed (update the structure section), or
   - you find a known issue or open question (add it to that section).

If either file has a merge conflict, keep both sides' lines; never delete another person's entry.

At the start of a session, read `PROGRESS.md` to understand the current state before changing code.

## Before opening a PR

1. Run `npm run build` and `npm run lint` and fix errors.
2. Check the changed pages in the browser (or Lovable preview after merge).
3. Describe what changed, how to test it, and include a screenshot for UI changes.
